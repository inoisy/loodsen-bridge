# Очередь проливки

git01 серверу виден только через мост с Мака: пуш — пока Мак не спит и в VPN, API git01
(MR, слияние, деплой) — никогда. Не жди Мак и не проси человека: клади работу в очередь, она лежит
на сервере и уходит сама, как только Мак ответит (проверка раз в 5 минут).

## Ветка и MR в git01

После коммита в своей ветке, из каталога репо:

```sh
deploy-queue add mr --branch <ветка> --target <база> \
  --title '<тип>(<scope>): <описание>. T-<номер>' --description-file mr.md --issue <KEY задачи multica>
```

- Ветка снимается в зеркало очереди сразу — каталог рана можно не беречь. Есть мост — пуш тут же.
- `mr.md`: первая строка — ссылка на задачу Сферы
  (`https://<sphere-host>/workgroups/group/<group_id>/tasks/task/view/<id>/`), при `T-12345` — без неё.
  Подписи ИИ очередь не пропустит.
- MR открывает Мак; сливают люди после ревью. В базовые ветки (`main`, `master`, `dev`, `develop`,
  `stage`, `prod`, `release/*`) очередь не кладёт.
- Перебазировал ветку после прошлой постановки — `add mr … --force` (перезапишет ветку в git01).
- Положил ещё коммиты в ту же ветку — тот же `add mr`: элемент обновится, новый не заведётся.

В отчёте вместо ссылки на создание MR — id элемента и что показал `deploy-queue show <id>`:
`push` (ждёт моста), `ready` (ветка в git01, ждёт MR), `done` + ссылка на MR, `failed` + причина.

## Сервис ресурсного планирования — в прод сам

Влил в `main` репо РП (`agent-merge`, приёмка маршрута) — больше ничего не нужно: синк в git01
ставит `rp-prod`, Мак сливает `main → dev → prod` и жмёт `deploy_prod`. MR в git01 для РП не открывать.
Посмотреть — `deploy-queue list`; встало в `failed` (конфликт в `dev`/`prod`, упала сборка) —
напиши это в итоговом комментарии, чинит человек.

## Посмотреть

```sh
deploy-queue list            # что ждёт
deploy-queue list --all      # и сделанное
deploy-queue show <id>
```
